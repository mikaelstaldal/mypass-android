# AI coding agent instructions

This file provides guidance to AI coding agents when working with code in this
repository.

## Project

`pw-android` is a native Android password manager (Kotlin, Jetpack Compose).
It is the phone companion of [`pw`](../pw), the Rust command line password
manager, and reads and writes **the same vault file**: the standard Tarsnap
scrypt encrypted-data format, holding the same JSON envelope. A `pw.scrypt`
copied between the two must work in both directions, unchanged.

That compatibility is the project's central guarantee. Nothing about the file
format or the JSON envelope may change here without changing `../pw` to match,
and `InteropTest` (a known-answer fixture generated by the real `scrypt` tool)
fails the build if the codec drifts.

## Build

```sh
gradle assembleDebug       # debug build
gradle assembleRelease     # release build (R8 on)
gradle test                # unit tests — pure JVM, no device or emulator
gradle testDebugUnitTest   # the same, debug variant only
```

No Gradle wrapper — uses the system `gradle` command. `local.properties` must
point `sdk.dir` at the Android SDK.

## Architecture

The library half deliberately mirrors `../pw`'s three layers, file for file, so
the two can be read side by side:

1. **`crypto/ScryptFormat.kt`** (`src/scrypt_format.rs`) — pure byte codec for
   the scrypt encrypted-data format v0 (scrypt KDF, AES-256-CTR, HMAC-SHA256).
   Does no I/O and knows nothing about vault contents. The scrypt KDF comes
   from Bouncy Castle (`SCrypt.generate`, the only thing used from it); AES-CTR
   and HMAC come from the platform JCE.
2. **`vault/`** (`src/vault.rs`) — the JSON envelope
   (`{"version":1,"entries":[…]}`) inside the scrypt format, atomic writes
   (write to `.tmp`, fsync, rename, keep previous as `.bak`), owner-only
   permissions. Bare JSON arrays written by pw ≤ 0.1.x are still accepted on
   read. `Secret` and `Passphrase` live here.
3. **`data/`** (`src/lib.rs`) — domain operations and input validation:
   `PwRepository` (the operations plus the unlocked-vault state the CLI does
   not need), `Matching`, `Validation`, `PasswordGenerator`, `Settings`.

   `PwRepository` has **two locks, for two different jobs**, and both matter:
   a coroutine `Mutex` serializes the slow work (the KDF and the file write),
   while a plain `stateLock` monitor guards the state machine — the passphrase,
   the auto-lock deadline, the expiry timer and every read or write of
   `_state`. Do not touch any of those outside it. `lock()` is callable from
   any thread at any moment, and a `lockEpoch` counter it bumps is what stops
   an unlock still grinding in the KDF from reopening the vault behind it.
   Auto-lock is **timer-driven**, not only checked on access: a screen sitting
   on a revealed password asks nothing of the repository, so without the timer
   it would never relock.
4. **`ui/`, `MainActivity`** (`src/main.rs`) — the Compose UI. All prompting,
   clipboard and biometric handling lives here; the layers below never prompt.
5. **`autofill/`** (`src/bin/pw-browser-host/` + `webextension/`) — the Android
   autofill service, this app's counterpart of the Firefox native-messaging
   host. The matching rules it relies on live in `data/Matching.kt` so they are
   unit-tested, and the two decisions inside the service that are worth testing
   are split out of the Android-bound walker for the same reason:
   `FieldClassifier` (what a field is) and `FormSelector` (which pair of fields
   is the form to answer for). Both are free of Android types; keep them that
   way. Which box is the username is desktop pw's rule, not an Android
   invention: a field that identifies itself, else the nearest text input
   *preceding* the password in the same form — `webextension/fill.js`'s
   `findUsernameField`, which is why `FieldKind.TEXT` exists and why
   `FormSelector` decides it rather than `FieldClassifier`. Name-matching alone
   cannot see a username box rendered as a bare `<input type="text">` with
   `autocomplete="off"`, which is common. When that rule changes there, change
   it here. `AutofillStructureParser` is only the tree walk and origin
   inheritance, where origin and container are separate questions: a node's own
   origin declaration decides its origin, while `FormContext.fieldContainer`
   decides what it is *part of* from its ancestors alone, because browsers
   annotate every field of a frame-spanning form with that frame's origin and
   reading each annotation as a document boundary leaves no two fields in one
   form. `descend` still resets the enclosing form below such a node.
   `FillDiagnostics` is the opt-in record of *why* a request produced no offer,
   which every refusal here needs because the framework gives a service no way
   to explain itself. It is Android-free and unit-tested; keep it that way,
   keep it off by default and in memory only, and keep field contents and
   entry names out of `FillRecord` — a test asserts its field list for exactly
   that reason. `FormSelector` reports which rule refused through
   `FormDiagnosis`, which must never feed a fill decision.

Errors are layered the same way: `ScryptFormatException` → `VaultException` →
`PwException`, with `PwRepository.mapVaultException` mapping low-level failures
to user-meaningful ones (wrong-passphrase vs corrupt-vault vs I/O stay
distinct).

There is no dependency injection framework. `PwApplication` holds the single
`PwRepository` and `Settings`; ViewModels are `AndroidViewModel`s that reach
them through the application.

## Secret handling conventions

- Passwords are wrapped in `Secret`, the master passphrase in `Passphrase`.
  Both are redacted by `toString`. The only way a secret leaves either is
  `expose()` — named so every exposure site is greppable. **Keep it that way.**
- `Passphrase` holds UTF-8 bytes and wipes them in `close()`; derived keys and
  the decrypted plaintext buffer are wiped too. A password is a `String` and
  **cannot** be wiped on ART — do not add code or documentation claiming
  otherwise. See the security notes in README.md, which say so plainly.
- Never log decrypted data, on any path.
- Every window that can show a secret sets `FLAG_SECURE`.

## Browser integration conventions

The autofill service is deliberately stricter than most Android password
managers, because it inherits the desktop's model. Each of these is load-
bearing; do not relax one without saying so in README.md's security table:

- Only entries with a `url` are eligible. The entry `name` is never matched
  against a host.
- The **focused** field decides which form is answered. A page often carries a
  sign-in form and a registration form; taking the first password field in the
  tree answers for whichever comes first in the document, not the one the user
  is standing in.
- `https:` only, plus `http://localhost` and `http://127.0.0.1`. A missing
  scheme is refused, not assumed to be `https:`.
- A `webDomain` is believed only from a package with a pinned signing
  certificate in `autofill/Browsers.kt` or deliberate user certificate
  enrollment, because Android does not verify the claimed domain.
- Web pages only: native app screens are never filled, because an entry's
  association with a site is its `url`, and inventing a second kind would
  change the shared vault format.
- The service never writes the vault. Saving goes through
  `AutofillSaveActivity`, where the user confirms with the entry on screen.
- The origin comes from the password field's own node (or its nearest ancestor
  that declares one), so a cross-origin iframe cannot collect the outer page's
  credential.

Android's autofill framework never sees HTTP authentication challenges, so the
desktop's `exactly_matching_entries` / realm-narrowing path has no counterpart
here. The `realm` field is still stored, edited and round-tripped for desktop
interop — do not drop it.

## Testing conventions

- All tests are plain JVM unit tests under `app/src/test/`. The crypto, vault,
  matching, validation and generator layers have no Android dependencies, which
  is what makes that possible — keep it that way when adding to them.
- Default scrypt parameters (`N=2^17`) are deliberately slow; tests always use
  `logN = 12`.
- `MatchingTest` is a port of `../pw`'s matching tests, case for case. When one
  changes there, change it here — a divergence is a divergence in which sites
  may receive which credential. Two of its cases guard normalization parity
  rather than matching logic, and their expected values were measured from the
  Rust `idna` crate itself: **hostnames are normalized with ICU's UTS #46
  non-transitional processing, never `java.net.IDN`**, which implements the
  older IDNA2003 and folds the deviation characters (`faß.de` becomes
  `fass.de`, and final sigma folds, which diverges for most Greek words ending
  in one). That is why `com.ibm.icu:icu4j` is a dependency rather than
  `android.icu.text.IDNA`: the latter is free but invisible to JVM unit tests,
  and this is the code that most needs testing against what actually ships.
- `PwRepositoryTest` runs the repository's clock, timer *and* KDF on the test
  scheduler (`StandardTestDispatcher`), so auto-lock is tested by advancing
  virtual time. Leaving the KDF on `Dispatchers.Default` makes `runTest`
  fast-forward to the next delayed task while the real thread works — which is
  the auto-lock expiry — and relock the vault mid-test. For the same reason,
  never wrap a suspending repository call in `runBlocking` inside `runTest`:
  it deadlocks. Use the `assertFailsWith` helper.
- `InteropTest` runs against `app/src/test/resources/known_answer.scrypt`, the
  desktop repository's own fixture (`../pw/tests/data/known_answer.scrypt`),
  generated by scrypt 1.3.2 with
  `scrypt enc --logN 12 -r 8 -p 1 --passphrase file:<passphrase-file>`.

## Other notes

- `minSdk` is 28 because `AssistStructure.ViewNode.getWebScheme()` arrived
  there, and without it the `https:`-only rule cannot be enforced. Do not lower
  it without a different answer to that.
- The app requests no network permission, and `backup_rules.xml` /
  `data_extraction_rules.xml` exclude everything from cloud backup and device
  transfer. Both are deliberate.
- Release builds run R8; `proguard-rules.pro` exists mainly to let it strip the
  unused 90-odd percent of Bouncy Castle and Guava quietly.
- Three third-party libraries, each for exactly one thing, and none of them
  casually: Bouncy Castle for `SCrypt.generate`, Guava for the Public Suffix
  List, ICU4J for UTS #46. Guava stops at the PSL, so `Matching` fills in the
  list's own implicit `*` rule for unrecognised TLDs — without it `.example`,
  `.internal` and every other unlisted TLD would match differently here than in
  desktop `pw`.
- ICU4J ships ~38 MiB of data for the 99% of itself this app does not use, and
  R8 cannot strip it because it is Java resources, not classes. `packaging` in
  `app/build.gradle.kts` excludes everything UTS #46 does not read, which is
  the difference between a 16 MiB and a 5 MiB release APK. Nothing in the build
  can prove that exclusion is safe, so **`tools/verify-icu-data.sh` does** — it
  runs every assigned code point through UTS #46 with and without the excluded
  data and requires identical output. Run it when bumping the ICU version or
  editing the exclusion list.
